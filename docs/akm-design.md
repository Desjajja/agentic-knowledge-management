# AKM 设计方案

日期：2026-10-12  
状态：设计基线，尚未实现  
名称：AKM（Agentic Knowledge Management），暂定

## 1. 目标与已确认需求

建立一个以 Obsidian 为本地知识存储与浏览工具、以 pi 为主要 Agent 运行时的知识协同系统。参考 claude-obsidian（以下简称 CO）的可靠性设计，独立实现领域模型与交互。

用户可以在对话结束后手动触发知识归档，也可以上传文档或指定 inbox 文件进行摄取。两种入口共用提案、关联分析、确认和事务写入流程。

已确认的约束：

- 对话归档由用户主动触发，不自动记录所有对话。
- 文档输入支持文件上传、显式指定文件及 inbox 批次。
- 候选知识以 `[1]`、`[2]` 等稳定 label 展示，支持修改、合并、剔除、暂缓和选择性写入。
- 人工主要审核内容、project、tags、aliases、related 及写入动作。其他状态由系统维护，只有冲突或必要决策才打断用户。
- project 是知识模块、索引根与迁移边界；不保留 scope 这一重复抽象。
- 每个正式知识页面必须有项目归属。个人偏好、通用方法、领域知识同样归入相应项目模块。
- 新项目在提案中明确显示 `[新创建]`，确认后才创建。
- 只有明确查询时才启动知识库问答；归档工作流可以读取已有知识以去重、匹配项目和提出关联。
- pi 为主运行时，允许第三方 OpenAI-compatible provider，配置仅作用于对应 AKM 工作区。
- Codex、Claude Code 等通过通用接口调用，可从任意工作目录使用，并支持异步查询。
- 用户不必记忆或重复提供路径。初始化后使用默认知识库，也可以按名称选择知识库。
- 完整 Vault 可通过整体复制或移动目录备份、迁移。单个项目通过模块导出处理跨项目依赖。

## 2. 概念与边界

| 概念 | 定义 | 边界 |
| --- | --- | --- |
| AKM 安装 | CLI、知识核心、pi 集成和输入解析器 | 与用户知识分离，可独立升级 |
| AKM 根目录 | 默认配置、工作区和知识库的统一管理入口 | 初始化时创建，用户可以改位置 |
| 工作区 workspace | pi 运行配置、提示词和 Vault 绑定 | 模型配置的生效边界 |
| 知识库 Vault | Obsidian 可打开的独立目录 | 完整备份、迁移和知识事务的边界 |
| 项目 project | 某个工作项目或长期知识领域的模块 | 页面归属、模块索引和导出边界 |
| 提案 proposal | 尚未正式提交的知识及修改建议 | 可编辑、恢复、选择性确认 |
| 来源 source | 文档或已授权对话片段及其出处 | 原始证据与生成知识分开保存 |
| 事务 operation | 一组经过检查的文件变更 | 提交、冲突检测和故障恢复的单位 |

工作区与知识项目不是同一概念。例如，一个工作区可以使用某个 provider 操作个人 Vault，而这个 Vault 包含“个人协作系统”和“分布式系统”两个项目。

Obsidian 不要求页面必须属于 project。这是 AKM 为模块化管理制定的规则。`project` 和 `related` 是自定义 Properties；`tags`、`aliases` 是 Obsidian 有特殊行为的属性。

## 3. 架构

```text
用户 / Codex / Claude Code / 其他 Agent
                 ↓
          CLI + JSON contract
                 ↓
       AKM 服务与 pi 编排运行时
       ├── 对话提取、文档理解
       ├── 查询回答
       └── 提案编辑与审阅
                 ↓
              知识核心
       ├── Vault、项目与页面解析
       ├── 来源保存与证据记录
       ├── 检索、链接与索引
       ├── 事务检查、提交与恢复
       └── lint 与模块导出
                 ↓
           Obsidian Vault
```

外部 Agent adapter 第一版采用 `SKILL.md`：说明如何发现知识库、调用命令、传递上下文、处理提案、读取异步结果以及取得写入授权。Skill 不包含具体机器路径。

CLI 是第一种对外接口，后续可以增加 MCP 等适配器。外部 Agent 使用同一套协议，不直接操纵交互式 pi 会话。文件检索、事务校验等确定性操作由知识核心执行，不必每个步骤都调用模型。

## 4. 默认目录与自动发现

以下是 AKM 自定义的建议布局，不代表 pi 原生配置文件格式。

```text
~/.akm/
├── config.json                     # 默认工作区与默认 Vault
├── workspaces/
│   └── default/
│       ├── workspace.json          # provider/model 引用、Vault 绑定
│       └── .pi/                    # pi 扩展、提示词与运行配置
└── vaults/
    ├── personal/
    │   ├── vault.json              # 稳定 ID、名称、描述、格式版本
    │   ├── index.md                # 人可读的项目导航
    │   ├── .obsidian/
    │   ├── inbox/
    │   ├── .raw/                   # 不可变来源副本
    │   ├── sources/                # 可读的来源记录
    │   ├── projects/
    │   │   ├── 个人协作系统/
    │   │   │   ├── project.json    # 模块 ID、描述、依赖声明
    │   │   │   ├── index.md
    │   │   │   └── 协作偏好.md
    │   │   └── 分布式系统/
    │   │       ├── project.json
    │   │       ├── index.md
    │   │       └── 幂等事件处理.md
    │   ├── .akm/                   # 必须保留的结构化知识记录
    │   │   └── ledgers/            # 来源、证据与正式操作记录
    │   └── .vault-meta/            # 提案、任务、事务恢复状态与派生索引
    └── work/
        └── ...
```

`vault.json`、`project.json` 及各级 `index.md` 使内容可自描述。页面与模块使用稳定 ID；目录名称用于阅读，身份不依赖原机器绝对路径。元数据和可读索引通过同一次事务同步维护。

定位规则：

1. 显式传入的 Vault 名称或 ID。
2. 显式选择工作区所绑定的默认 Vault。
3. AKM 根配置中的默认 Vault。

没有默认库或名称匹配有歧义时，展示名称与描述让用户选择。当前目录不自动成为知识库，也不要求放置绑定文件。整库迁移后通过根目录扫描或一次重新登记恢复定位。

根配置对内部工作区和 Vault 使用相对路径。`--vault` 接受名称/ID；低层管理命令可以接受路径，但常规交互不暴露路径。

## 5. 项目归属与链接

项目既可以是“项目 Alpha”，也可以是“个人协作系统”“通用方法”等长期模块。

建议第一版每个页面有一个主归属项目，其他项目通过引用或依赖使用它。这能避免单页多归属带来的导出与更新歧义；多归属支持尚未定案。

用户审核的正式 Properties 示例：

```yaml
---
project: 项目 Alpha
tags:
  - sync
  - architecture
aliases:
  - 服务端同步方案
related:
  - "[[项目 Alpha/事件版本号|事件版本号]]"
  - "[[通用方法/幂等事件处理|幂等事件处理]]"
---
```

实际生成的链接需解析到明确页面路径。展示给用户时可以使用简短标题；重名时显示项目归属。

`related` 可以跨项目。展示跨项目关系时附简短项目名称，便于用户判断归档与导出影响。未找到的目标标为 `[未找到]`，拟创建的页面标为 `[新创建]`，不把猜测的页面当作已存在链接。

系统记录模块内关系、外部依赖及一般参考关系。能够从页面归属判断的关系无需人工填写；确实影响导出的语义歧义才询问用户。

## 6. 提案交互协议

最小展示单元：

```text
[1] 服务端负责最终同步状态
客户端仅保留临时缓存，重新连接时从服务端恢复状态。

项目：项目 Alpha
标签：#sync #architecture
别名：服务端同步方案
相关：同步架构；幂等事件处理（通用方法）
动作：更新「项目 Alpha/同步架构」
```

没有有用别名或关联时可省略对应行，不为了填满字段生成信息。显示内容和目的页面，不能只展示标题与 metadata。

系统内部维护提案 ID、版本、证据评估、生命周期、冲突及目标文件哈希。正常情况下不展示这些字段。事实冲突、失效引用或语义不清需要用户决策时，用简短说明指出具体问题。

label 规则：

- 在一个提案批次内稳定，不因删除而重排。
- 追加项使用新编号；内部 ID 与显示编号分开。
- “合并 [2] 到 [1]”保留 `[1]`，`[2]` 标为已合并。
- 旧编号不能静默指向另一条知识。
- 不同批次通过提案 ID 区分，恢复时保留编号。

支持自然语言和结构化编辑：保留、剔除、暂缓、修改内容/属性、合并到候选项或已有页面、查看正文/来源。

确认针对当前提案版本和明确的选择集合。用户直接说“确认写入 [1]、[3]”即可授权相应版本；不要因内部检查再次索取相同确认。内容发生实质变化、扩大写入范围或目标已被修改时，返回必要的差异供重新审阅。

## 7. 工作流与模拟输入输出

### 7.1 对话归档

```text
用户：整理本次对话，归档到工作知识库。

Agent：
[1] 服务端负责最终同步状态
客户端只保留临时缓存。
项目：项目 Alpha
标签：#sync #architecture
相关：同步架构；事件版本号
动作：更新「项目 Alpha/同步架构」

[2] 状态不一致排查顺序
依次检查事件幂等性、版本号和缓存失效策略。
项目：项目 Alpha
标签：#debugging #sync
别名：状态不一致排查
相关：同步架构；幂等事件处理（通用方法）
动作：新建「项目 Alpha/状态不一致排查」

用户：[2] 标签增加 #distributed-systems；[1] 保留。

Agent：已修改 [2]。准备更新同步架构、新建排查页面，
       并更新项目 Alpha 索引；其他页面保持原内容。

用户：确认写入 [1]、[2]。

Agent：已写入：更新 1 页，新建 1 页，更新项目索引。
       来源入口已附在页面中。
```

输入必须由调用方显式提供可访问的对话消息及范围；CLI 无法凭一个会话 ID 读取所有平台的历史。adapter 负责提供内容，并说明有无缺失上下文。

默认保存支持已选知识点所需的对话片段及消息标识，不归档完整对话。具体片段保留策略在实现前确定。用户补充的解释也需记录为新的来源，而非冒充原文证据。

### 7.2 文档摄取

```text
用户：处理 inbox/architecture.md。

Agent：
[1] 事件版本号用于过滤过期更新
接收端比较事件版本号，仅应用更新版本。
项目：项目 Alpha
标签：#sync #versioning
别名：事件版本控制
相关：同步架构
动作：更新「项目 Alpha/事件版本号」

[2] 离线同步的恢复流程
恢复连接后，先同步服务端状态，再重放本地待处理事件。
项目：离线同步研究 [新创建]
标签：#offline #sync
相关：同步架构（项目 Alpha）
动作：新建项目索引与恢复流程页面

用户：[2] 改归属为项目 Alpha，不新建项目；确认写入 [1]、[2]。

Agent：已写入：更新事件版本号页，新建离线恢复流程页，
       更新项目 Alpha 索引。原文副本和来源记录已保存。
```

本地来源先做只读预检；来源捕获若已获授权，可以独立完成，不表示知识提案自动批准。最终知识提交必须引用已保存来源，或在提交中同步保存来源。失败的捕获不能留下已确认摄取标记。

上传文件由调用方提供可读取的本地文件或内容，系统存入 inbox 或直接捕获。不能假定所有 Agent 都能读取附件。

解析能力按实际实现声明。Markdown/文本作为首批能力；PDF 等格式需实际解析器与抽取验证，不能把“记录文件元数据”宣称为“读懂全文”。无法完整解析时明确反馈。

### 7.3 显式检索与异步调用

```text
用户：结合学城资料和知识库，解释 Alpha 的同步设计。

外部 Agent：并发查询学城，并提交 AKM 知识库查询。
AKM：立即返回任务 ID。
外部 Agent：处理学城结果，再读取 AKM 任务结果。
AKM：返回相关页面、可引用片段、来源定位和必要限制。
外部 Agent：综合两边证据回答，并保留各自来源。
```

普通对话不自动检索或注入热上下文。显式查询不修改正式知识页面；归档时内部匹配已有内容不等于开启每轮对话检索。

## 8. 对外接口草案

以下命令是待实现的 AKM 协议示例，不是当前可用命令：

```bash
akm init
akm vault list --json
akm query --query "同步架构有哪些已确认决策？" --json
akm query --vault work --query "同步架构" --json
akm query submit --vault work --query "同步架构" --json
akm job status <job-id> --json
akm job result <job-id> --json
akm job cancel <job-id>
akm ingest --vault work --file inbox/architecture.md --json
akm extract-conversation --input conversation.json --json
akm proposal edit <proposal-id> --input edits.json --json
akm proposal inspect <proposal-id> --json
akm proposal apply <proposal-id> --revision <reviewed-revision> --items 1,2
akm operation recover --vault work
akm project export --vault work --project "项目 Alpha" --output alpha.zip
akm vault doctor --vault work
akm vault lint --vault work
```

协议需提供版本、请求 ID、结果/错误区分和稳定错误码。异步任务支持 queued、running、completed、failed、cancelled，结果持久化并可重复读取。提交进程退出后任务仍应继续，由独立 worker 或服务执行。

查询结果至少包含页面定位、匹配片段、引用信息和限制说明；模型总结可选。查询可能写入任务记录或派生缓存，但不能隐式归档回答、改动知识正文。

Codex 位于 dirA、工作区和 Vault 位于 dirB 时，CLI 自动读取默认配置；调用方无需切换目录。外部 Agent 能否执行 CLI、访问本地服务仍取决于其工具与权限。

## 9. Provider 与 pi 隔离

每个 AKM 工作区独立声明 provider、base URL、模型与凭据引用。第三方 OpenAI-compatible 接口的具体兼容能力需通过适配验证。

凭据来自环境变量或系统密钥存储，不放入知识库。AKM 启动 pi runner 时显式应用对应工作区配置，不能修改 pi 全局 provider，也不能影响其他工作区。

此前讨论中的 `.pi/models.json` 是未经验证的示意，不能作为实现依据。实施前需核对 pi 的实际扩展/SDK/config 接口，验证两个工作区之间模型配置隔离及异步 runner 生命周期。

## 10. 事务、证据与检索

从 CO 参考的工程原则：

- 产品、用户 Vault 与派生运行状态分离。
- 保存不可变、内容寻址的来源副本。
- 来源和关键主张之间有可追踪证据关系。
- 一次知识提交对应一个可恢复事务，包含页面、属性、项目索引及必要 ledger 更新。
- 提交前核对目标文件哈希或预期不存在状态，发现外部修改即报告冲突。
- 使用 Vault 级写锁、恢复日志、备份和单文件原子替换。
- 不允许 Agent 工具或 Obsidian CLI 绕过知识核心写入。
- 只读 lint、可重建检索索引、明确的外部解析与网络调用边界。

多文件事务的应用过程不保证外部 Obsidian 读者永远看不到中间状态；核心需保证操作可恢复，并使自身查询获得一致版本或明确重试。具体并发实现待技术设计确定。

用户仍可在 Obsidian 中编辑页面。核心在提交前检查变化、检索时识别过期索引，不能强制要求用户只通过 AKM 修改知识。

证据评估由系统维护，但“用户批准归档”不等于“该主张已被外部事实验证”。若存储置信信息，它必须依据证据与冲突状态，而不是模型自信程度。

本地检索先提供确定性的全文/BM25 能力；向量检索为可选增强，失败可回退。检索范围按显式 Vault 和项目选择，不引入 scope 对象。

## 11. 备份、迁移与项目导出

### 完整 Vault

停写或使用一致文件系统快照后，整体复制/移动 Vault 目录即可保留知识资产，不需要另行导出数据库。

- 页面、附件、来源副本、证据 ledger 和模块描述全部位于 Vault 内。
- 不依赖外部原始文件路径维持证据；捕获后使用本库来源副本。
- 内部引用使用 Vault 内链接、相对路径和稳定 ID。
- 派生索引可以重建；事务恢复日志不能作为普通缓存随意删除。
- 迁移后旧进程锁不得直接沿用，需检查恢复状态。
- 根目录内自动扫描恢复登记；移到根目录外时一次重新绑定即可。

复制 Vault 即可迁移知识库。若还要迁移工作区和模型设置，可复制整个 AKM 根目录；应用程序需另行安装，凭据需在新环境重新提供。

### 单个项目

单独复制项目目录不能保证来源与跨项目链接完整，使用项目导出生成完整模块包：页面、索引、来源、必要 ledger 子集与模块 manifest。

导出时检查所有出站内部引用，不能遗留无说明的失效 Wikilink。可选策略：包含依赖、生成可读外部引用页、保存依赖快照。外部引用页只保证引用可解释，不代表完整知识已包含；要求完整离线内容时必须包含依赖或快照。

导出需同步重写链接，避免占位页再次引用未打包的目标。默认策略尚未确定，导出预览中明确展示影响。

## 12. 最小验收场景

| 场景 | 预期结果 |
| --- | --- |
| 新环境初始化 | 创建默认根目录、工作区及自描述 Vault；后续无需提供路径 |
| 从任意工作目录查询 | 调用默认库，或按库名定位；不误用当前目录 |
| 对话归档 | 展示最小候选信息；只保存明确选择的内容 |
| 编辑/删除/合并提案 | label 稳定，未选项不提交，合并可追踪 |
| 新项目 | 显示 `[新创建]`，用户确认后同事务创建索引和页面 |
| 文档摄取 | 正文确实可解析；保存来源副本；共用提案流程 |
| 与 Obsidian 同时编辑 | 检测目标变化，不静默覆盖 |
| 提交中断 | 恢复到可解释的一致状态，不遗留半完成知识记录 |
| 异步查询 | 提交后立即返回；任务独立运行，可读取/取消/报告失败 |
| 工作区模型隔离 | 工作区 A 的自定义 provider 不影响 B 或全局配置 |
| 整库迁移 | 正文、来源、模块归属保留，索引可重建，链接不依赖旧绝对路径 |
| 单项目导出 | 所有内部链接有目标或明确的外部引用说明 |

- 项目导出的默认外部依赖策略。
